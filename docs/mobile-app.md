# React Native App

The Ozealis companion app lives in `mobile/`. It is a React Native app built with Expo and native BLE support.

Because BLE requires native modules, this app needs an Expo development build. It will not run as a full BLE client inside plain Expo Go.

Native BLE metadata is configured for the app's central/client role. The Expo BLE plugin uses `modes: ["central"]` so iOS receives `bluetooth-central` background capability only; the app does not advertise as a BLE peripheral. Android BLE permissions are generated by the plugin with `neverForLocation: true`, so Android 12+ scan permission is marked as not used for location while older Android releases can still request the legacy location permission required for BLE scanning.

## Install

Use Node.js `22.x` for mobile commands; `mobile/package.json`, `mobile/package-lock.json`, and CI all pin that major version.

```bash
cd mobile
npm ci --ignore-scripts
npm run check:expo
npm run test:operation-lease
npm run test:live-evidence
npm run test:session-report
npm run test:graph-downsampling
npm run test:session-archive
npm run typecheck
npm run test:web-export
```

## Run

From `mobile/`, run a browser layout preview without BLE hardware:

```bash
npm run web
```

There is no `npm run build` script in `mobile/package.json`; use `npm run web` for local web preview. `npm run test:web-export` performs a temporary Expo web export smoke so browser-preview bundle regressions are caught during local verification, requires both `index.html` and a non-empty generated JavaScript bundle, then removes the generated output.

From `mobile/`, create and install an Expo development build for native BLE control:

```bash
npm run android:dev-build
```

iOS native builds require macOS and can be created with `npm run ios:dev-build`. These commands run Expo's native `run` workflow and may generate the ignored `mobile/android/` or `mobile/ios/` directory.

After the development client is installed, use `npm run start`, `npm run android`, or `npm run ios` to start Metro and launch the existing client. The `android` and `ios` scripts do not create a development build.

Expo Go and the browser are useful for layout checks only. Browser preview stays in BLE preview mode and must not construct the native BLE manager; the BLE path uses `react-native-ble-plx`, so end-to-end scan, connect, telemetry, settings, start/stop, calibration, logs, and OTA flows need the native development build on real hardware.

The firmware marks settings, control/start-stop, OTA command/status, session and fault logs, motor-calibration status/command, and MCF8316D parameter snapshots as encrypted. Android or iOS may show a BLE pairing prompt the first time the app reads or writes one of those characteristics.

## Current capabilities

- Scan for Ozealis BLE devices.
- Stop scans, clear stale scan results, clear pending scan timeouts, clear pending automatic log-import bookkeeping, and clear stale connected-session state when connecting, disconnecting, Bluetooth powers off, telemetry subscription monitoring fails, or the app unmounts. Every completed connected-session reset advances the generation so a second callback carrying the old generation cannot reset or publish again. Each Ozealis or oximeter scan request also claims one synchronous shared scan admission before the permission prompt, awaits native stop/start promises, reads live manager Bluetooth state instead of a render-captured value, revalidates that exact admission and both connection/source transitions after every await and immediately before and after native scan dispatch, and releases only its own scan state. Cross-kind replacement waits for native stop before installing the new listener; callbacks require their advertised service UUID, so a queued result from the previous scan family cannot select the new listener's path. Disconnecting or resetting the oximeter synchronously revokes any reconnect scan admission and timeout before cancellation. Connect closes the previous connected-device ref and claims a synchronous transition owner before its first `await`; disconnect does the same before transport cleanup. Delayed destructive or motor-moving callbacks must verify their captured device still matches the current connected session before writing. Manual disconnect cleanup must run even if the platform BLE close call reports an error, so the app does not keep stale write eligibility after a local disconnect.
- Serialize every foreground Ozealis BLE transaction that owns the app busy state through one synchronous, exclusive operation coordinator bound to the exact `{deviceId, sessionId, operation}` triple. Current-session leases cover settings read/write, retained-log read/clear, MCF8316D snapshot read, motor-fault clear, OTA, start/stop/prewarm control, and calibration start/water-start/capture/abort. The same coordinator reserves `connection:connect` and `connection:disconnect` transition tokens, so double taps cannot overlap connection attempts or closes, connection bootstrap protocol/settings/driver reads cannot overlap the relay, and stale transition cleanup cannot clear or cancel replacement work. Connect validates its exact transition after relay drain, device connect, MTU negotiation, service discovery, and every bootstrap read. Disconnect preempts an active foreground lease, makes the session unavailable synchronously, and initiates target cancellation without waiting on a possibly hung relay write. Foreground code checks the exact token and connected session after every awaited boundary, immediately before a state-changing transport write, and before publishing readback, success, or error state. Only the exact active token may release the lease and clear busy, so an invalidated stale `finally` cannot unlock or overwrite replacement work. Starting a new connection generation, beginning disconnect, Bluetooth loss, telemetry-subscription failure, connected-session reset, and app unmount revoke outstanding leases synchronously. Bluetooth loss also tombstones the exact connection and source transition owners, so recovery does not depend on a native connect promise settling; late candidate cleanup skips any in-flight or committed same-device replacement. Unmount also nulls the connected identity and advances its generation before asynchronous BLE cancellation, so a delayed confirmation cannot acquire a fresh token after teardown. Delayed log-clear, OTA, and water-start confirmations retain the device/session that opened the prompt and acquire only inside the confirmed callback; a callback from an older session sends nothing. Scanning uses the separate exact admission described above; passive telemetry/subscriptions, local exports, and the separately session-scoped latest-only PLX relay do not acquire a current-session foreground lease. Lease admission clears queued relay work, waits for any relay write already dispatched to finish before the first foreground BLE transaction, and makes later relay samples drop while foreground or transition work owns the transport. This coordinator is app-local race and lifetime control only: it cannot retract a write already handed to the platform BLE stack and is not authorization, firmware interlocking, or a safety boundary.

## Known limits

- BLE pairing currently depends on the operating system "Just Works" flow unless future hardware adds a display, keypad, or commissioning button flow.
- The app does not provide an app-layer authorization boundary.
- OTA commands are not a trusted production update channel until signed-image verification, certificate pinning, or an equivalent documented authenticity design exists.
- Low-flow index and heuristic airflow-window labels are engineering review aids only; they are not diagnostic, screening, treatment, or efficacy outputs.
- `SessionReportV1` is a deterministic summary of accepted experimental evidence, not an authenticated record or clinical report. Device uptime cannot establish a wall-clock session, capture/import anchors do not synchronize the device clock, and report hashes cannot establish who or what produced a measurement.
- Motor calibration still requires external pressure/current instrumentation and a known bench test load. Default firmware requires verified MCF8316D I2C speed-command readback before nonzero motor command is accepted; PWM speed command is an explicit bench firmware opt-in only.
- Firmware currently keeps a rolling 30-minute 1 Hz session buffer in RAM. The app captures a higher-rate 60-minute live trace only while Bluetooth stays connected and commits that latest window plus a device/session-bound manifest to app documents storage. Retained imports reject the whole session/fault pair on duplicate or backwards timestamps or a missing/foreign sample kind; graphs, summaries, day filtering, and heuristic airflow windows ignore retained calibration evidence and use only the latest cadence-consistent airflow-run segment. Live capture starts a new source when device/session identity changes or after a sufficiently large backwards timestamp jump or over-cadence forward gap, so replacement, rebooted, or paused traces are not stitched together. If Bluetooth disconnects, graphing and stop-time import derate to the latest retained 1 Hz window while the last connected live trace remains exportable but is not attributed to a later connection. A manual evidence archive preserves only the bounded source window captured at save time; it does not recover earlier rolling data or turn the app into a continuous full-night recorder.
- The app should be tested on real Android hardware with a flashed ESP32 before tagging a release.
